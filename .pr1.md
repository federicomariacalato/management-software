## Problem

The date-range filter on `/orders` silently drops orders depending on the viewer's timezone.

Order dates are plain `YYYY-MM-DD` strings, so `new Date(order.date)` is parsed by the spec as **UTC midnight**. `react-day-picker` hands back **local midnight** `Date` objects. `Orders.tsx` compared the two directly:

```ts
new Date(order.date) >= dateRange.from &&
  (!dateRange.to || new Date(order.date) <= dateRange.to)
```

Two separate failures fall out of this:

1. `dateRange.to` is midnight, so every order on the **last selected day** falls *after* it and is excluded (positive UTC offsets).
2. In negative UTC offsets the order parses to the *previous* local day, so the **first selected day** is excluded.

Reproduced by replicating the predicate and selecting 11 Sep -> 12 Sep:

| Timezone | Orders returned | |
|---|---|---|
| `UTC` | `["09-11","09-12"]` | ok |
| `Europe/Rome` | `["09-11"]` | **end day lost** |
| `America/New_York` | `["09-12"]` | **start day lost** |
| `Asia/Tokyo` | `["09-11"]` | **end day lost** |

It only behaves correctly for users on UTC — i.e. almost nobody. The demo on Vercel is in a European timezone, so it is affected today.

## Fix

Extract the predicate into a pure `src/utils/orders.ts` and normalise both sides to **local day boundaries** before comparing:

- the order date is parsed as local midnight via ``new Date(`${order.date}T00:00:00`)``
- `from` becomes start-of-day, `to` becomes **end-of-day** (`23:59:59.999`)

This also keeps working for the intermediate state where `react-day-picker` sets only `from` (single-day selection), which previously had no explicit coverage.

Verified across `UTC`, `Europe/Rome`, `America/New_York`, `Asia/Tokyo`, `Australia/Sydney`, `Pacific/Kiritimati` (UTC+14) and `America/Sao_Paulo`, for both full and single-day ranges: all pass.

The filtering logic now lives in one testable place instead of inline in a page component, which is the groundwork for the test suite.

## Also included

The search box matched only `customerName` and `email`, while the table displays an `Order Id` column. Searching for `#10460` — the exact lookup a support agent has to do — returned nothing. `id` is now part of the search predicate, plus a `.trim()` so a stray space no longer silently narrows results.

## Risk

Low. Contained to the filter predicate; status filtering is unchanged. `tsc -b` and `vite build` both pass.

This is the first of a small series; a test suite for the derivation layer follows separately so this PR stays reviewable on its own.
